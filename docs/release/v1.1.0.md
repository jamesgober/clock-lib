# v1.1.0 — Time You Can Control

`clock-lib` 1.1 fixes a monotonicity bug in the mock clock and fills the gaps that made the mock clock hard to use in real code. Readings now convert to and from `std::time`, monotonic readings support deadline arithmetic that never panics, `ManualClock` can start at a fixed time and step wall time on its own to simulate an NTP correction, and the `Clock` trait gained the `elapsed` method that keeps injected-clock code honest. Everything is additive: code written against 1.0 compiles and behaves the same, except that the overflow bug is gone.

```toml
[dependencies]
clock-lib = "1.1"
```

## Highlights

- **`ManualClock` can no longer go backwards.** `advance` used `fetch_add`, which wraps; two `advance(Duration::MAX)` calls moved the clock backwards. It now saturates, as the 1.0 docs promised.
- **Deadline arithmetic.** `start + ttl`, `deadline - now`, `checked_add`, `saturating_add`. None of it panics, so `now + Duration::MAX` is a usable "never".
- **Interop.** Lossless `From` conversions between `Monotonic` and `Instant`, and between `Wall` and `SystemTime`. Any time source can now implement `Clock`.
- **Reproducible timestamps and NTP tests.** `ManualClock::with_start(wall)` pins wall time; `step_wall_back` / `step_wall_forward` / `set_wall` move wall time without moving monotonic time.
- **`Clock::elapsed`.** Measure through the injected clock. The free `elapsed` reads the OS clock, and the docs now say so wherever it matters.
- **`Deadline` and `Stopwatch`** on any clock, **RFC 3339 `Display`** for `Wall`, **signed Unix accessors** for pre-epoch times, and opt-in **`serde`** and **`web-time`** features.

## What's New

### Fixed

- `ManualClock::advance` wrapped the offset on cumulative overflow, so `now()` and `wall()` could move backwards. It is now a lock-free compare-and-swap loop with `saturating_add`; the offset stops at `u64::MAX` ns (about 584 years). Regression tests cover both reproductions from the audit, contended multi-threaded overflow, and loom models.
- `ManualClock` readings at extreme offsets clamp to the platform's range instead of panicking.
- Documentation errors: `duration_since` does not panic (it saturates); daylight-saving time does not move Unix time; `ManualClock` deltas are deterministic, and absolute timestamps now are too with `with_start`; Windows wall time has 100 ns granularity (now documented and tested); `wasm32-unknown-unknown` panics without `web-time`; the performance page no longer claims an enforced CI gate or identical assembly.
- `cargo test --no-default-features` compiles and runs.

### Added

- **`Monotonic`**: `checked_add`, `checked_sub`, `saturating_add`, `saturating_sub`; operators `+`, `-`, `+=`, `-=` with `Duration` (saturating); `Monotonic - Monotonic -> Duration` (saturating); `From<Instant>` and `Instant: From<Monotonic>`.
- **`Wall`**: `UNIX_EPOCH`; `from_unix_seconds` / `from_unix_millis` / `from_unix_nanos`; `checked_add`, `checked_sub`; `unix_seconds_signed`, `unix_millis_signed`, `unix_nanos_signed`; `From<SystemTime>` and `SystemTime: From<Wall>`; `Display` as RFC 3339 UTC (no allocation, precision and padding supported).
- **`Clock`**: provided method `elapsed(&self, since)`; `impl Clock for Box<C>`.
- **`ManualClock`**: `with_start`, inherent `now` / `wall`, `advance_to`, `step_wall_forward`, `step_wall_back`, `set_wall`, `set_auto_advance`, `auto_advance`.
- **`Deadline<C = SystemClock>`** and **`Stopwatch<C = SystemClock>`**.
- **Feature `serde`**: `Serialize` / `Deserialize` for `Wall`, byte-for-byte the same format as `std::time::SystemTime`.
- **Feature `web-time`**: browser time on `wasm32-unknown-unknown`; no-op and no dependency elsewhere.

### Changed

- `Monotonic::duration_since` is explicitly saturating rather than delegating to `Instant::duration_since`. Same result on every supported toolchain; immune to a future std change.
- The `no-std` crates.io category is gone, and the docs say exactly what `default-features = false` provides: a compiling crate with only `VERSION`.
- The published package ships only source, tests, benches, README, CHANGELOG, `docs/API.md` and the licenses.
- Tooling: criterion 0.7 with `std::hint::black_box`; CI runs real stable, beta, MSRV, wasm, loom, docs.rs and semver-checks; actions are current and the toolchain action is SHA-pinned; dependabot is on.

### Security

No vulnerabilities affect `clock-lib` users. The dev-only RUSTSEC-2026-0204 lockfile refresh (crossbeam-epoch via criterion) that landed after 1.0.0 is now recorded in the CHANGELOG, and crossbeam is no longer in the development graph at all.

## Performance, Re-Measured

Re-measured on 2026-10-13: AMD Ryzen 9 9950X3D, Windows 11 Pro 10.0.26200, Rust 1.85.0, criterion 0.7, medians. The 1.0.0 column is a fresh run of the 1.0 code with identical benchmark bodies in the same session. Full tables are in [PERFORMANCE.md](../PERFORMANCE.md).

| Bench | 1.0.0 | 1.1.0 | Notes |
| --- | --- | --- | --- |
| `std::time::Instant::now` | 23.74 ns | 25.09 ns | raw std, the noise reference |
| `clock_lib::now` | 23.71 ns | 23.63 ns | within noise of std |
| `Monotonic::now` | 23.80 ns | 24.33 ns | within noise of std |
| `std::time::SystemTime::now` | 20.82 ns | 22.86 ns | raw std moved +9.8% on unchanged code |
| `Wall::now` | 21.18 ns | 23.44 ns | +2.5% vs std in the same run |
| `clock_lib::elapsed` | 27.14 ns | 25.87 ns | |
| `Monotonic + Duration` | &mdash; | 777 ps | `Instant + Duration`: 790 ps |
| `Deadline::is_expired` | &mdash; | 25.37 ns | hand-written check: 26.78 ns |
| `Wall` RFC 3339 `Display` | &mdash; | 132 ns | no allocation |
| `ManualClock::now` | 777 ps | 854 ps | +1 relaxed load (auto-advance) |
| `ManualClock::wall` | 839 ps | 3.39 ns | +1 relaxed load and branch (wall-only steps) |
| `ManualClock::advance` | 4.18 ns | 4.16 ns | saturating CAS loop costs nothing over `fetch_add` |

The OS-clock paths stay within noise of raw `std::time`. Two `ManualClock` paths got slower. `now` pays one extra relaxed load (+10%). `wall` pays a second atomic load and a branch for wall-only stepping, about 2.5 ns per call. That exceeds the REPS 5% budget for that one metric, and it was accepted on purpose: it is the price of `step_wall_*`/`set_wall`, every alternative layout measured the same, and a million `wall()` reads still cost about 3.4 ms in a test.

## Compatibility

- **SemVer:** minor release. Every change is an addition: new methods, new trait implementations, a provided trait method, new types, and opt-in features. No signature changed and nothing was removed. `cargo-semver-checks` against 1.0.0 reports no breaking change.
- **MSRV:** Rust 1.85 (unchanged), including the `serde` and `web-time` features.
- **Edition:** 2024.
- **Platforms:** Linux, macOS, Windows; `wasm32-unknown-unknown` with `web-time`; compiles for `no_std` targets with default features off (exposing only `VERSION`).
- **Behaviour changes users could notice:** `ManualClock::advance` past `u64::MAX` total nanoseconds now saturates instead of wrapping. That was the documented behaviour and the wrap was a bug. `ManualClock`'s `Debug` output has new fields.

## Upgrading From 1.0

Bump the version. No code changes are required.

```toml
[dependencies]
clock-lib = "1.1"
```

Worth adopting:

- In code that takes a `Clock`, replace `clock.now().duration_since(stamp)` and any `clock_lib::elapsed(stamp)` with `clock.elapsed(stamp)`.
- Replace `(start, ttl)` pairs with `start + ttl` or a `Deadline`.
- Pin test clocks with `ManualClock::with_start(Wall::from_unix_seconds(..))` for stable snapshots.

## Not in This Release

- **A real `no_std` clock.** `Monotonic` wraps `std::time::Instant`, so a core-only reading type is a 2.0-sized change.
- **A thread-local mock mode** for code that calls the Tier-1 functions directly. It needs global state, which conflicts with the dependency-injection design; `Clock` remains the supported way to mock time.
- **A coarse or cached clock.** It needs an upkeep thread or platform FFI. For now, use `quanta` or `coarsetime` when a sub-10 ns read matters.
- **RFC 3339 parsing, calendars and time zones.** Out of scope; use `chrono`, `time` or `jiff`.

## Stability Promise

Anything documented in [docs/API.md](../API.md) is part of the 1.x contract. Behavioural changes that would break correct downstream code will only ship with a major version bump. The 1.0 notes said future 1.x work would not add APIs; the 2026 audit showed that additive APIs were exactly what the mock clock needed, and additions remain fair game for minor releases.
