# v1.2.0 - Mixed clocks caught in debug builds

`clock-lib` 1.2 catches a mistake the type system could not: measuring a `ManualClock` reading against the operating system clock. It also builds under a downstream `RUSTFLAGS="--cfg loom"` again. No public item is added, removed, or changed; MSRV stays 1.85, and there is no new dependency.

```toml
[dependencies]
clock-lib = "1.2"
```

## Readings of different clocks

`Monotonic` and `Wall` cannot be mixed: the compiler refuses. Readings of two different monotonic clocks could be: a reading from a `ManualClock` and one from the operating system are both `Monotonic`. Code that takes a `C: Clock` but somewhere calls `stamp.elapsed()` or `clock_lib::elapsed(stamp)` measured real time in tests and ignored every `advance`, and a deadline built from a manual reading on the system clock waited in real time. Because the manual clock is anchored at a real `Instant`, the wrong answers looked plausible.

In debug builds every reading now remembers its clock, and these panic when given readings of different clocks, with a message that says what to call instead:

- `Monotonic::elapsed` and `clock_lib::elapsed` on a `ManualClock` reading;
- `duration_since`, `checked_duration_since`, `saturating_duration_since`, and `reading - reading` across clocks, which also covers `Clock::elapsed`, `Deadline`, and `Stopwatch` given a foreign reading.

```rust
let clock = ManualClock::new();
let stamp = clock.now();
clock.advance(Duration::from_secs(3600));
clock.elapsed(stamp);        // 3600 s, as before
stamp.elapsed();             // debug build: panics; release: real time, as before
```

Same-clock use is unchanged. Comparisons (`==`, `<`) and conversion to `std::time::Instant` are not checked. Release builds keep a bare `Instant` and check nothing, so readings cost the same as in 1.1.

A test suite that measured a manual reading with the OS clock on purpose now panics in debug builds; measure it with `clock.elapsed(stamp)`.

## Builds under a downstream `--cfg loom`

1.1.0 gated its loom model checks on the conventional `cfg(loom)` with `loom` as a dev-dependency. A crate that model-checks its own code sets `--cfg loom` for every crate in its build, so `clock-lib` failed to compile there. The checks now use the crate-specific `clock_lib_loom` cfg, and only this crate's own unit tests switch to loom atomics under it: `loom` stays a dev-dependency, and every build of the library uses `core` atomics. CI now builds and tests a throwaway downstream crate under `--cfg loom`, with a `ManualClock` inside and outside a `loom::model`.

## Documentation

`step_wall_forward` and `step_wall_back` now say to call them from the test driver, as `set_wall` already did: a `wall()` on another thread at the same moment can combine the old offset with the new adjustment.
